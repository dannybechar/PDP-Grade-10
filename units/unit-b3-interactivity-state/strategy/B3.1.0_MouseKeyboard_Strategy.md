# B3.1 — Mouse and Keyboard Events

**Strategy document** | Unit B: Creative Programming | B3: Interactivity & State

## Position and scope

B3.1 introduces event-driven behaviour across three 45-minute lessons:

1. **B3.1.1 — Mouse Events**
2. **B3.1.2 — Keyboard Events**
3. **B3.1.3 — Combining Events**

The first two lessons separate continuous held/live values from discrete callbacks. The third
combines both input sources and previews persistent state without duplicating B3.2's deeper state
model.

## Learning objectives

Students should be able to:

- Read `mouseX` and `mouseY` inside `draw()` to track the pointer.
- Distinguish `mousePressed` from `mousePressed()` and use `mouseReleased()`.
- Distinguish `keyPressed` from `keyPressed()` and inspect the printable character in `key`.
- Explain the keyboard-repeat caveat for a held key.
- Combine a mouse callback and a keyboard callback in one sketch.
- Change class-level values in callbacks and render their current values in `draw()`.

## Technical decisions

- Every Processing lifecycle or event callback shown in BlueJ uses `public void`.
- `draw()` remains present so events are processed and state changes are rendered continuously.
- `background()` clears prior frames when a tracked shape should not leave a trail.
- Core keyboard examples compare printable characters such as `key == 'a'`; `keyCode`, `CODED`,
  arrows, and special keys are optional extensions rather than required lesson content.
- Mouse scope is position plus press/held/release. Clicked, dragged, moved, and wheel callbacks
  remain outside the core lesson.
- A value shared by `draw()` and callbacks is declared outside all methods. B3.1 calls this a
  persistent sketch variable and leaves the full state concept to B3.2.

## Lesson progression

### Mouse input

Students build a pointer-following circle, compare held-state behaviour with a one-press callback,
and add a release action. They modify size or fill while the button is held and construct a
complete visible mouse response.

### Keyboard input

The same variable-versus-callback distinction is applied to the keyboard. Students compare a
specific printable key, observe held-state rendering, and design two visibly distinct character
key responses without shorthand conditions.

### Combined events

One callback changes size while another changes grayscale or position. `draw()` reads both
persistent fields, making the separation between input/update and rendering explicit.

## Misconceptions to surface

- `mousePressed` and `mousePressed()` are not interchangeable.
- A callback changes data; it does not need to redraw the whole scene itself.
- A held key can trigger repeated callbacks through OS key repeat.
- A variable local to one method cannot be shared with another callback.
- Without `background()`, a moving shape leaves retained pixels rather than being cleanly erased.

## Assessment evidence

Students classify live fields and callbacks, predict callback counts for press/hold/release
sequences, and construct one program in which mouse and keyboard events update different visible
properties.

## Implementation status

Implemented in `01-mouse-events` through `03-combining-events`. The three revised presentations
align with nine runnable BlueJ projects, all of which compile independently against Processing
4.5.6. Printable-character checks form the core keyboard path; special-key handling is not needed
for completion.
