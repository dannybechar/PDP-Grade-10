# B3.4 — User-Controlled Parameters

**Strategy document** | Unit B: Creative Programming | B3: Interactivity & State

## Position and scope

B3.4 closes B3 by applying event/state/rendering to adjustable numeric properties across two
45-minute lessons:

1. **B3.4.1 — Key-Controlled Parameters**
2. **B3.4.2 — Mouse Regions & an On-Screen Button**

Here “parameter” means a running program property such as size, speed, quantity, or visual
intensity. This differs from B2.1's function parameter, which is a named input in a method
definition; the student materials state that distinction explicitly.

## Learning objectives

Students should be able to:

- Increment and decrement a persistent numeric value from key events.
- Keep that value inside a sensible range.
- Distinguish a discrete stepped control from a continuously read control.
- Drive a value directly from `mouseX` or `mouseY` in `draw()`.
- Draw a visible button and test whether a click lies inside its rectangular region.
- Keep drawing geometry and hit-test boundaries synchronized.

## Technical decisions

- Bounds use nested explicit `if` statements so key repeat cannot drive the value indefinitely.
- Suggested step values divide the chosen range cleanly; arbitrary steps require clamping or a
  post-update correction that is not needed for the core example.
- Continuous control reads `mouseX` directly. `map()` is not introduced because the 400-pixel
  canvas already supplies a useful demonstration range.
- A button is a drawn `rect()` plus four inclusive boundary checks in `mousePressed()`.
- The four checks are nested rather than combined with `&&`.
- Hover feedback repeats the same explicit region logic and must not use ternary shorthand.
- Sliders, drag tracking, widget libraries, and compound conditions remain outside the two-hour
  scope.

## Lesson progression

### Key-controlled value

`+` and `-` change a circle size by a fixed step. Students trace minimum, middle, and maximum
cases, observe OS key repeat, then construct a second bounded parameter such as grayscale
intensity.

### Continuous input and button region

Students first set size from the live mouse x-coordinate, contrasting continuous reading with an
event step. They then draw a button, derive left/right/top/bottom boundaries from its geometry,
and reset or change state only when a click passes all four checks.

## Misconceptions to surface

- A visible rectangle is not a control until input logic tests its region.
- Changing the rectangle without changing the hit test creates an invisible interaction mismatch.
- Inclusive edge checks make clicks on the visible border count as inside.
- A live mouse coordinate does not need a callback to be read continuously.
- A control changes state; `draw()` renders the state's current value.

## Assessment evidence

Students test bounds repeatedly, explain discrete versus continuous control, test inside/outside
and all four button edges, and construct one control mapped to a meaningful program property.
