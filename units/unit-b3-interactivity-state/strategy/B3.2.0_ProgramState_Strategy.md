# B3.2 — Program State

**Strategy document** | Unit B: Creative Programming | B3: Interactivity & State

## Position and scope

B3.2 names and generalizes the persistent-variable pattern across two 45-minute lessons:

1. **B3.2.1 — What Is State?**
2. **B3.2.2 — Using State**

Program state is treated as remembered information whose current value can affect future
behaviour or display. Class-level fields are the representation used in these sketches, but the
concept is defined by meaning rather than by a memorized placement rule.

## Learning objectives

Students should be able to:

- Identify which values in a sketch are meaningful changing state.
- Distinguish state from fixed configuration and temporary local calculation.
- Trace frame-driven, event-driven, and condition-driven state updates.
- Separate writing state from reading state.
- Use current state directly as a visual parameter or in a condition that selects behaviour.
- Construct and test a two-state interaction with an explicit initial value and transition rule.

## Technical baseline

- State fields are declared outside all methods so values persist and remain accessible to
  `draw()` and event callbacks.
- Frame-driven updates use each `draw()` call as one time step, not an exact elapsed-time unit.
- Event-driven updates occur in callbacks and become visible when `draw()` next reads the field.
- Condition-driven updates may reverse a speed or choose another state value.
- Core mode examples use `int mode` with `0`/`1` or named constants, avoiding String equality.
- Explicit `if`/`else` replaces ternary shorthand. Separate conditions replace compound OR tests.

## Lesson progression

### Identify and update state

Students compare fixed values with fields whose current value matters, then trace three update
triggers: a per-frame position, a mouse-updated size, and a condition-reversed speed. A simple
one-dimensional bounce demonstrates a condition changing state rather than only appearance.

### Read state to determine behaviour

Students first feed a state value directly into a property, then use an integer mode to choose
between two visibly different outputs. An event updates the mode; `draw()` reads it. This complete
write–remember–read cycle prepares the scene model in B3.3.

## Misconceptions to surface

- Not every class field is meaningful changing state; some values are fixed configuration.
- A callback's assignment is not visible unless rendering reads the updated value.
- Testing a held-state field inside `draw()` can repeat a toggle many times.
- Position is updated before a boundary check in the model bounce, so a large speed can overshoot.
- State and its visual representation are related but not the same thing.

## Assessment evidence

Students annotate update and read sites, trace several frames/events, explain the initial state and
transition rule, and construct a two-mode program whose current state produces clearly different
outputs.

## Implementation status

Implemented in `04-what-is-state` and `05-using-state`. The two revised presentations align with
six runnable BlueJ projects, all of which compile independently against Processing 4.5.6. The
project examples use explicit branching rather than ternary or compound-condition shorthand.
