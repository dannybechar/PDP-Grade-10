# B3.3 — Multi-Scene Flow

**Strategy document** | Unit B: Creative Programming | B3: Interactivity & State

## Position and scope

B3.3 scales state-driven branching into a complete three-scene program across three 45-minute
lessons:

1. **B3.3.1 — Naming Scenes**
2. **B3.3.2 — Transitioning Scenes**
3. **B3.3.3 — Complete Flow**

The visual throughline is a title/introduction scene, a play/main scene, and an end scene. Every
lesson retains that concrete flow so the work does not become an abstract state-machine lecture.

## Learning objectives

Students should be able to:

- Represent scene identities with named `final int` constants.
- Keep the changing current scene in a separate state field.
- Render exactly one scene from the current value.
- Update scene state from mouse or keyboard callbacks.
- Guard a transition so an input is meaningful only from the correct starting scene.
- Construct and test a closed multi-scene flow, including reset behaviour.

## Technical decisions

- Scene identity uses integers, not Strings, avoiding `.equals()` and reference-equality pitfalls.
- Constants such as `SCENE_INTRO`, `SCENE_MAIN`, and `SCENE_END` improve readability without
  introducing `enum`.
- `draw()` displays the current scene; it does not automatically advance the scene every frame.
- Event callbacks update `scene`; they do not draw the destination scene directly.
- Guarded transitions use nested `if` statements, not `&&`.
- Scene display uses explicit `if`/`else if` or mutually exclusive comparisons, not ternary
  expressions or `switch`.
- Timers, animation systems, scene objects, and formal finite-state-machine notation remain out
  of scope.

## Lesson progression

### Name and render scenes

Students distinguish immutable scene constants from the mutable `scene` field, temporarily change
the initial scene to test each branch, and add a third distinct output.

### Transition between scenes

A mouse press changes intro to main. A keyboard event changes main to end only when both the
current-scene guard and key check pass through nested `if`s. Students replace one input source and
add a valid transition to their third scene.

### Complete flow

Students assemble title → play → end plus a deliberate reset route, trace allowed and ignored
inputs from every scene, and test the transition table rather than only the happy path.

## Central invariant

At any moment `scene` contains exactly one defined scene constant. Each event either assigns one
valid next value or leaves the current value unchanged. Rendering never changes `scene` as a side
effect.

## Assessment evidence

Students produce a transition table, narrate event → assignment → next rendered scene, and build a
three-scene program in which invalid inputs are safe no-ops and the reset route is verifiable.

## Implementation status

Implemented in `06-naming-scenes` through `08-complete-flow`. The three revised presentations
align with nine runnable BlueJ projects, all of which compile independently against Processing
4.5.6. Complete examples use named integer constants and explicit guarded transitions.
