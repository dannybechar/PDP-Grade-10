# B2.4 — Conditions for Procedural Variation

**Strategy document** | Unit B: Creative Programming | B2: Parameterized & Procedural Creation

## Position and scope

B2.4 applies familiar `if`/`else` syntax to generated visuals across two 45-minute lessons:

1. **B2.4.1 — Conditions That Vary Appearance or Behaviour**
2. **B2.4.2 — Combining Conditions with Loops and Functions**

The sequence closes B2 by composing its mechanisms. It does not use mouse or keyboard input;
interactive conditions begin in B3.

## Learning objectives

Students should be able to:

- Evaluate one comparison for representative values before predicting output.
- Use an `if`/`else` rule to vary fill, size, or position.
- Distinguish the value a condition checks from the visual property its branch changes.
- Place a condition inside a parameterized drawing method.
- Call that method from a loop and, where useful, pass a bounded random value into the rule.
- Explain the separate responsibility of the method, loop, random sample, and condition.

## Technical decisions

- Core examples use one comparison at a time, such as `x < 220`, `i < 3`, or `value > 50`.
- Compound `&&`/`||`, modulo, ternary expressions, `switch`, and chained decision trees remain
  outside B2.4.
- Position, loop counters, parameters, and generated values are all valid condition inputs.
- A condition may vary appearance or behaviour; the syllabus's examples are choices, not a
  checklist requiring every property.
- The synthesis program generates its stable result once in `setup()`.
- Simple boundary behaviour becomes conceptually possible here, but collision systems and general
  edge handling are not needed to satisfy this learning statement.

## Lesson progression

### One rule, visible effect

Students evaluate a position threshold and a loop-counter threshold, predict which iterations use
each branch, then modify a cutoff and construct their own six-shape rule.

### Composition

The rule moves into `drawMarker(x, y, value)`. A loop calls the method repeatedly, and a bounded
random value can determine which branch runs. Students label each layer before constructing a new
combination with a chosen threshold and visible result.

## Misconceptions to surface

- The value being checked does not have to be the property being changed.
- `else` begins at the first value for which the comparison is false; boundary values matter.
- A condition inside a method is evaluated separately on every call.
- Random input to a condition does not make the entire structure uncontrolled.
- Combining known mechanisms does not require compressed shorthand syntax.

## Assessment evidence

Students trace branch decisions for exact values, predict the effect of a changed threshold, and
construct a method-plus-loop program in which the rule and both outcomes can be explained clearly.

## Implementation status

Implemented in `09-conditions-appearance` and `10-combining-conditions`. The two revised
presentations align with six runnable BlueJ projects. All six compile independently against
Processing 4.5.6; project examples use the same explicit single-comparison style as the lessons.
