# B1.4 — Read, Trace, and Deliberately Modify

**Strategy document** | Unit B: Creative Programming | B1: The Draw Loop & Creative Environment

## Position and scope

B1.4 is one approximately 60-minute lesson and closes B1. It introduces no new Processing API.
Its new demand is independence: students read a working sketch they did not write, predict its
behaviour, make a small purposeful change, and compare the result with their prediction.

## Learning objectives

Students should be able to:

- Identify the roles of `settings()`, `setup()`, and `draw()` in an unfamiliar sketch.
- Classify fields and local variables and explain what each stores.
- Trace update order across several frames.
- Predict the visible result before running the code.
- Predict the effect of one specified change, implement it, and evaluate the outcome.

## Technical baseline

Every sketch uses only established B1 mechanisms:

- canvas and coordinate conventions;
- rectangles, ellipses, lines, and persistent style state;
- local and persistent sketch variables;
- `background()` and repeated drawing;
- fixed increments, signed velocity, and combined changing properties.

The code is syntactically valid and runnable. Compiler-error diagnosis, new drawing APIs,
conditionals, transformations, collections, and formal object-oriented reasoning are not part of
this learning statement.

## Lesson progression

1. Teacher models a structured first read: lifecycle, variables, execution order, output.
2. Students annotate a second unfamiliar sketch independently before running it.
3. Students record a prediction for a small change such as a sign, initial value, increment, or
   local style setting.
4. Students edit, compile, run, and compare evidence with the prediction.
5. The class distinguishes an incorrect prediction from an incorrect implementation.

## Trace protocol

For each sketch, students answer in this order:

1. What happens once?
2. What repeats?
3. Which values persist?
4. Which values are local to one call?
5. In what order are values updated and drawn?
6. What should appear before the program is run?

This repeatable protocol transfers directly to later units, where programs become longer but the
same reading questions remain useful.

## Assessment evidence

The final evidence is not simply a successful run. Students submit or explain the original trace,
the predicted change, the edited line, and whether the output confirmed the prediction.

## Implementation status

Implemented in `08-read-trace-modify`. The revised presentation and five runnable projects cover
teacher modelling, independent tracing, local-style modification, and signed-velocity
modification. All five BlueJ projects compile independently against Processing 4.5.6.
